# S5-08 Animation, Audio & Copy Polish Design Contract

**Status: accepted corrected design; Design Freeze candidate until independent documentation review, protected merge, main Linux Quality and Recovery Test all succeed.** This document is a design contract, not an implementation or evidence of completed S5-08 effects. The Specification, Development Protocol, S0-06, frozen Stage 1–4 contracts and S5-01–S5-07 contracts retain precedence. `PROJECT_STATUS` supplies the effective single Next Action.

## 1. Scope and authority

S5-08 adds disposable character/Board/Item/Reward/Benben/terminal feedback, Settings-controlled music and sound effects, and complete centralized working-language copy. It consumes the single production session and guarded Save v4 authority through the existing S5-02 presentation root. Nothing in S5-08 decides, delays or triggers a gameplay transition, Reward claim, tutorial acknowledgment, Save write or retry. UI, Scene, audio and animation have no second Runtime, Board truth, event log, writer, queue, Manager or Event Bus. Stage 6 retains full bilingual delivery, skins and mobile certification; S5-09 retains whole-presentation integration certification.

The corrected sequence is:

```text
one immutable operation envelope -> existing session.execute
  -> exact committed result + trusted pre-dispatch state
  -> detached, sanitized one-shot effect handoff
  -> immediate authoritative public projection/render
  -> stable accessible/text feedback
  -> optional cancellable visual effect and bounded sound
```

Ordinary `read()`, `reload()`, ViewModel reconstruction, `draw()`, `paint()`, resize, route return and F5 can show committed facts but **cannot create an operation-specific effect**. A rejected, stale, lease-lost, storage-failed, unknown or uncertain result cannot create a success effect. `commit-commit-outcome-uncertain` is never replayed; `commit-persistence-commit-failure` retains the existing conservative discard/reload policy absent exhaustive promotion evidence.

## 2. Exact operation-bound effect provenance

The trusted `systems/presentation` adapter owns a page-local opaque operation identity assigned when it creates the S5-02 immutable envelope. This identity is technical correlation only: it is not a production intent field, gameplay RNG, Save fact or UI authority. A retained Retry uses the **same original envelope and identity**, including its original semantic `intent.kind`; a Retry button's action name is not the operation kind. Changed player choice, discarded envelope or browser reload creates no continuation of that identity.

Only the branch in which that envelope's `session.execute` returns `committed` may construct the handoff. The adapter privately checks the envelope's expected revision/runId against its captured pre-dispatch authority and uses that exact result Runtime/revision, not a later `session.read()` or `reload()`. It supplies separately detached/frozen sanitized public `before` and `after` facts, the original operation kind, opaque identity, and the existing S5-07 `RewardReceiptProof` and `firstLucky` proof. Raw Runtime, runId, seeds, hidden Mine identity, unclaimed Reward, one-time claim ID, generation provenance and mutable aliases never reach `ui`, Scene or audio. `systems/presentation` owns the handoff output type; `ui` owns the structurally exact input type and pure cue projector; only bootstrap/root checks the complete nested compatibility and passes values across S0-06's import boundary. No systems-to-ui or ui-to-systems import is introduced.

The root dispatches this handoff at most once per committed identity. It is transient page memory, not a persisted event ledger. The cue projector may use only the operation kind, proven receipt/Lucky facts and same-operation public before/after facts. A generic committed/save message remains valid even when a specialized proof is insufficient. In particular:

- Reward celebration requires `RewardReceiptProof.status === 'proven'` with nonempty entries; multiple Airplane entries remain one operation. No balance/inventory delta, later claimed summary or F5 can infer a receipt. Insufficient proof suppresses celebration, not committed rendering or the existing diagnostic.
- Lucky-specific feedback requires the existing `firstLucky` proof on that committed Move. Inventory presence or `revealed-mine-occupancy` alone is insufficient.
- Detection, Revive, Airplane, Benben claim/eligibility and terminal cues require the matching committed operation and enough same-operation public transition facts. The UI does not recalculate eligibility, hidden candidates, failure rolls, victory or resource priority. If temporary-versus-Account consumption cannot be proven from the trusted result, use a generic Item success cue rather than assert its source.
- Navigation-only changes and wrapper results lacking the exact committed operation handoff do not receive specialized operation effects. Background music is governed by validated public Settings, not an operation effect.

This is a narrow additive presentation-result interface; it does not enrich or reinterpret the Stage 4 production mutation result. Tests must reject forged/reused handoffs, mismatched identity or revision, secret fields and aliases.

## 3. Rendering, accessibility and visual-effect lifetime

The bootstrap's committed-result handler first invalidates an older effect epoch, then synchronously renders the new authoritative public ViewModel. It next updates a stable page-lifetime text/status surface, including accessible outcome and Reward wording, and only then dispatches optional decoration. Text is not waiting on a tween, sound, asset load or animation-complete callback. Claimed Reward and current Account/Attempt facts remain readable from the public ViewModel after an effect is skipped, interrupted or cancelled. An event-only receipt may be missed by immediate F5; it is never replayed from saved facts.

One page-local monotonically increasing `effectEpoch` is invalidated by a newer committed result, route change, layout/resize invalidation, explicit or required reload, Recovery, authority-dirty notification, Scene shutdown/disposal and HMR/full reload. Every tween, timeout, asset completion and sound-effect callback checks its epoch and owning Scene/route before touching presentation. Ordinary base `draw()`/`paint()` and ViewModel reconstruction neither increment an otherwise valid epoch nor emit a cue. Phaser retains one committed base drawing and a separate disposable effect layer; DOM retains its sole board input surface. Decorative pixels do not accept pointer input, block legitimate rapid commands, write Save, or overwrite a newer committed position. A resize may cancel rather than replay an effect; base geometry is redrawn from the latest ViewModel. `prefers-reduced-motion` may shorten/omit decoration without adding a persisted preference.

The stable accessible/text outcome is updated once per meaningful result and survives ordinary redraw or effect cancellation during that page visit; it is not a durable event log or a substitute for S5-07 claimed summaries and tutorial progress. Rejected/no-op/stale/uncertain outcomes use their existing exact copy/reload policies, never a success announcement. Recovery keeps reload and Feedback usable without deleting or rewriting Save.

## 4. Authority invalidation and retained-operation safety

Foreground or cross-tab storage notification is an **untrusted signal of possible change**, not a new authority. Bootstrap immediately marks presentation authority dirty, increments the effect epoch, stops success cues and music, and shows a centralized reload-needed message. It neither interprets A/B slots nor calls a gameplay command. Until revalidation it cannot announce a new success or submit an ordinary new intent from a stale view.

Crucially, this signal alone does **not** call the existing broad `presentationRoot.reload()` or cancellation methods: those deliberately clear retained Game, Shop or replacement envelopes. A retained, precisely owned pre-commit Retry remains with its original immutable envelope and affordance, marked as requiring revalidation. The user's explicit Retry uses the existing `adapter.retryRetained()` path, which reloads committed authority and compares the original expected revision/runId before any re-execution. Match permits only that user-initiated exact-envelope retry; mismatch/stale/lease/unknown discards it and requires a new action. `commit-commit-outcome-uncertain` never gains a Retry. If the user instead explicitly chooses Reload, the existing root reload/reconciliation may intentionally cancel retained operations with the owning Game/Shop/replacement controls updated together. No unrelated envelope is silently destroyed for audio or visual convenience. A failed reload keeps non-destructive Recovery/reload access and all success effects suppressed.

This is a page-local presentation freshness gate, not a second saved authority. Its only release is a successful existing authority reload/reconciliation or a proven exact-envelope Retry outcome; it never treats `read()` or a storage event payload as proof of new committed facts. The current S5-05 Shop/Game route reconciliation remains in force. A foreground notification may conservatively require a user reload even when no saved fact changed; that usability cost is safer than applying an old envelope to unverified authority.

## 5. Page-lifetime audio and asynchronous playback

Bootstrap owns one disposable page-lifetime `audio` adapter. Routes/Scenes never create their own players. It consumes only validated current public `settings.musicEnabled` and `settings.soundEffectsEnabled`; the two persisted booleans remain the sole preference authority. Music is one background loop across normal routes, subject to a user gesture/browser permission and current visible, clean, non-Recovery state. One-shot sound uses only the §2 committed handoff. Set a small fixed concurrent voice limit and coalesce simultaneous cues from one operation; do not queue old sounds or play one sound per Reward entry without a bound. Audio failure is presentation-only and never changes a command or Save.

Every asynchronous `play()`/resume attempt has a generation token **and its own source handle**. Disabling the relevant Setting, authority becoming dirty, hiding the page, Recovery, disposal or a newer playback attempt invalidates the token and immediately pauses/stops that handle. Both promise resolution and rejection check the token. A late resolution/rejection for an expired attempt must stop its own old handle and may neither resume/sustain it nor pause a newer handle. Playback rejection remains silent with optional centralized accessible explanation; there is no `Math.random` fallback, automatic permission loop or deferred replay of prior one-shot sounds.

On cross-tab/foreground invalidation audio pauses before authority reconciliation. It adopts Settings only from a subsequent successful existing reload or exact committed result, never from storage event contents or an uncommitted checkbox. If hidden or permission-denied it stays silent. On return it resumes music only when visible, authority clean, Settings enabled and browser permission/user-gesture requirements are met; past one-shot sounds do not resume. Disposal removes listeners and stops handles.

## 6. Complete centralized semantic copy and assets

`config/presentation-copy.ts` remains declarative data. Add stable semantic keys containing **complete sentences** and typed parameter contracts for public coordinates, quantities, Item/resource names, claimed Reward, statuses and ARIA labels. A small pure `ui` formatter accepts `copy(key, validatedPublicParams)`; it selects resource-defined grammatical variants and places parameters/punctuation, outputs plain text through `textContent`, and has a safe missing-key/invalid-param fallback. UI/Scene supplies only detached public values, not raw Runtime, technical reason strings as prose, hidden facts or HTML. Existing exact reason-to-copy-key classification stays in the trusted presentation capability; the formatter does not become a rule engine. Tests cover visible and accessible sentences, plural/quantity variants, dynamic labels and missing resources. Stage 5 supplies polished working-language copy; Stage 6 owns full translation, language switching and bilingual layout.

Before any external asset is used, record its source, author, license text/link, permitted game/distribution use, attribution obligations, transformations and cost in a reviewable asset manifest. Verify attribution and license compatibility; a missing or unclear license blocks that asset, not gameplay. No purchase, paid service, commissioned artwork or other expenditure is authorized by this design; Elio must approve spending in advance. Existing/free self-owned placeholders may support implementation and tests without silently assuming commercial rights.

## 9. Remaining risks, recovery and next phase

Browser autoplay/visibility behavior varies; blocked playback must be silent, not a failed game operation. A user can miss a one-shot celebration by F5; already committed Reward/Account facts remain readable, without an event-log replay. Cross-tab localStorage still lacks atomic CAS; the existing guarded writer remains the authority. Production currently has one Level and no one-time Reward generation; controlled catalog and validated preloaded-v4 compatibility evidence must not be mislabeled as production content. Phaser bundle size remains an observation. Exact art/music taste, licensing and any spending require later review; none requires a new gameplay rule here.

Recovery from repository authority must identify Stage 0–4 FROZEN, Stage 5 IN PROGRESS, S5-01–S5-07 CLOSED, the single guarded Save v4 production authority, four corrected Attack boundaries, the §7.1 scope, future acceptance matrix, Stage 6 exclusions and the single effective Next Action from `PROJECT_STATUS`. Until documentation Reviewer, protected merge, main Linux Quality and final Recovery pass, this is a **candidate**, not a frozen contract. After those gates, only S5-08 Implementation becomes the next authorized phase; this document neither implements it nor starts S5-09.
