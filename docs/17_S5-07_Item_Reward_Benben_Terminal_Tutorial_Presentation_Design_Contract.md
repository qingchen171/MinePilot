The bootstrap-only structural handoff and exact nested type compatibility from S5-02 remain mandatory. No Item evaluator, reward ledger, Benben manager, terminal state machine, second session or Save path is authorized.

## 2. Committed outcomes and one-shot Reward receipts

Every Item, Failure, Benben claim, lifecycle and tutorial action follows semantic choice -> immutable S5-02 envelope (dispatch-time revision/runId and stable technical facts) -> existing production command -> validated candidate -> guarded Save v4 commit -> publish -> public projection. No UI mutation, extra writer, speculative position/resource/terminal success or animation-triggered command is allowed.

A Reward receipt is an ephemeral property of **one actual committed operation result**, not a persisted event log. The trusted adapter captures its pre-dispatch session authority and exact envelope, then compares that pre-state with `result.runtime` and `result.revision` returned by that same `session.execute`. It must not construct a receipt from a later `session.read()`/`reload()`, balance delta, cached ViewModel or another writer's state. For each receipt require all of:

1. The dispatched revision/runId matched the pre-state; committed result revision is `0` from no-save or exactly `N+1` from committed `N`. Reward receipts are only possible for `move` or `airplane`, with the same non-null runId and levelId before/after.
2. The complete Reward set retains the same identities (`runId + row-major coordinate`), count, coordinates, payloads and `oneTimeClaimId`s; the reported entry alone changes `claimed: false -> true`. No `true -> false` or duplicate identity is accepted. Its Safe coordinate is newly explored in the committed Board. Existing claimed Rewards remain claimed.
3. For a non-null one-time ID, that exact ID was absent from the pre-state Account claims and present exactly once in the committed Account claims; all prior claim IDs remain. A normal Reward has no fabricated one-time ID. The committed aggregate's ordinary validation remains controlling.
4. Only validated transitions become detached receipt entries (payload/coordinate/one-time marker, not the raw Runtime or ID). Sort by row-major coordinate. One Airplane commit may deliver multiple entries. Item consumption and Reward acquisition can offset in inventory, so net assets are never used to infer the receipt or its source.

The adapter returns the committed snapshot projected from **that result Runtime** with the one-shot receipt; the root hands both to the current view once. Subsequent `read`, `reload`, F5, route recreation and competing-writer reload yield only committed assets/claimed summaries, not another receipt. A failed, stale, lease-lost, storage-failed or uncertain result yields none. If any identity, revision, claim or payload proof is insufficient, omit the receipt, retain the committed authority display and surface a diagnostic; never manufacture a reward or replay the command to obtain feedback. Lucky success or a Benben card may be explained only from proven committed before/result facts; after-state alone must not assert an unproven resource source.

## 3. Input activation, retained Retry and Airplane target

Each S5-07 Item/lifecycle/tutorial control owns one native activation sequence. Disarm before synchronous submission; correlate pointer press/click/double-click continuation on the same control, keyboard down/up/repeat and browser-synthesized click so that one activation creates at most one envelope even if commit already returned. A click-only assistive activation remains usable once. A genuinely new independent activation is allowed immediately, including a second legal Detection use; no global time debounce, animation lock, persisted latch or second command queue. Cancel an outstanding key/press sequence on focus loss, route change, authority invalidation or control disposal. S5-06 board native-event semantics remain untouched.

The page-lifetime presentation root, not a Scene, owns a transient token identifying **the exact retained S5-07 envelope** and its owning Game/Shop prompt surface. Only a proven pre-new-head retainable rejection may display Retry. The Retry action uses the same immutable envelope after explicit reload and exact authority match; it never redraws runId, generation seed, Reward, Detection seed or Benben card. When leaving that owning surface, cancel only the matching token and remove its Retry affordance together. Kind-only matching is insufficient because S5-05 replacement can also retain `abandon`, `dismiss` or `start`. The precise-token extension must leave the S5-03 purchase latch/retry and S5-05 replacement ownership untouched; neither may be cancelled by S5-07 cleanup. Scene reconstruction on the same route may re-render an extant owned Retry; full browser reload drops it. Stale revision/runId, lease loss, conservative `commit-persistence-commit-failure`, unknown results and uncertain new-head outcomes discard the envelope and require the existing reload/recovery policy. `commit-commit-outcome-uncertain` is **never replayed**, even after reload.

The existing DOM board owns one explicitly highlighted public selected coordinate. Add only a readonly query returning a detached coordinate tied to a disposable board/authority epoch; no second hit surface, board truth or Scene target calculation. Airplane's button uses that selected coordinate at activation, validates the same current Game/Attempt/board epoch and submits the existing `airplane(coordinate)` semantic intent. No target means the button is unavailable; an invalid command is still rejected by production. Moving focus from a selected cell to its Airplane button keeps the visible target, just as the S5-06 Flag button does. Route/Attempt/authority change, reload, Recovery, board reconstruction or focus leaving the relevant Game control group invalidates it; after a committed board change, require a fresh current selection. The native desktop primary/secondary cell actions remain Move/Flag; keyboard focus alone never moves; touch mode remains separate. DOM stays the only board-input surface and Phaser only draws.

## 4. Gameplay and terminal presentation matrix

| Authority state / operation | Presentation contract |
|---|---|
| Active, waiting/on-board/occupancy | Show trusted Item controls. Detection needs an eligible active position, available matching temporary-or-account resource and usage below 2; hidden-target existence is not advertised. Airplane accepts an explicit valid selected center, including waiting; use cap 1 and no-benefit use may consume. Lucky is automatic on first actual Mine step, never a button. |
| Pending Mine encounter | Board input and Detection/Airplane are unavailable. Show the committed pending decision, legal Revive (temporary Revive first, then Account; cap 1; Lucky priority protected) or explicit Failure. Do not reveal Mine or claim failure before a commit. |
| Benben available | An offer may be deferred with no mutation. Only active + waiting + `hasTakenStep=false` may submit separate `claim-benben`; success atomically changes Account available -> used and creates one Attempt card. Three settled Failures per exact level cause a separate deterministic 3/10 eligibility roll; pending/Lucky/Revive survival do not count. Claimed card has frozen 3/3/1/3 Item weighting, is consumed before matching Account inventory, and expires at won/failed/replacement; no reroll, second grant or double consumption. |
| Failed | Present settled Failure facts, legal Retry/return/dismiss, retained Benben `available` offer for a future same-level Attempt. No Revive from failed, no automatic Retry, no temporary card resurrection. Historical missing-catalog Retry may reject; legal dismiss remains available. |
| Won | Present committed completion and claimed assets; Next only when trusted catalog/access says available, Replay/return via existing commands. No duplicate settlement or invented completion payout. On the current one-level production catalog, Next is unavailable. |
| Historical `legacy-excluded` terminal | Show actual phase and separately derived action restrictions. Settings/tutorial acknowledgment may return `not-writable`; do not hide legal Dismiss or assume old completion/Reward/Benben effects. Catalog-dependent replacement safely rejects if current level is unavailable. |

`Restart`, `Retry`, `Replay`, `Next`, Failure settlement, Benben claim and all Items use only existing production intents. Navigation to menus never implicitly abandons or dismisses; S5-05's ordinary cross-level two-commit flow and atomic Next/Replay remain separate. Successful Item/Reward/terminal display uses only committed projection. Domain rejection/no-op shows central copy; stale/lease loss requires reload/new action; unknown/uncertain does not show success; corrupt/unavailable Save enters non-destructive Recovery. F5 reconstructs the same Attempt, Board, resources, entitlement/card, phase and tutorial acknowledgments without re-triggering commands or one-shot receipts.

## 6. Protocol §7.1 frozen-boundary control

**Reason:** S5-07's real UI cannot safely express Item/Benben/terminal action status, provide operation-bound Reward receipts, identify a retained retry owner or hand an explicit Airplane target from the existing board with the current S5-02/S5-06 presentation API alone. The six Attack findings require narrow, additive presentation extensions.

**Affected frozen contracts:** S5-02 sanitized public projection/result boundary, one-shot committed-result feedback and exact retained-envelope ownership API; S5-06 DOM board's readonly selected-target interface. S5-01/S0-06 dependency and single-session rules and S5-03 Shop/S5-05 navigation ownership remain unchanged. Stage 1–4 gameplay, Account, Reward/Benben, Save v4 and Stage 2 persistence authority are not reopened.

**Compatibility impact:** Existing semantic command meanings, phase/Item legality, exact-string reason policy, uncertain/unknown conservatism, board Move/Flag semantics and UI import directions are preserved. New fields are detached advisory display data; final production command validation remains authoritative. `legacy-excluded` has per-command restrictions, not a blanket read-only interpretation. Existing Shop purchase and replacement retained operations remain isolated.

**Schema/version/migration:** None. No Save v4 field, `CURRENT_SAVE_VERSION` change, migration, new RNG or new production Level. Receipts, target selection, activation and retained-owner tokens are ephemeral and never serialized.

**Regression plan:** §7, plus existing Stage 1–4 Item/Reward/Benben/terminal/Save v4 and S5-02–S5-06 navigation, input, Shop, Settings/tutorial, architecture and recovery suites. Secret-field/no-alias checks and actual guarded-session/browser failure injection are mandatory. **Rollback:** reviewed scoped revert of future presentation extensions; no Save downgrade, destructive reset or claim/inventory adjustment. This assessment is the explicit approved S5-07 design-level change-control boundary; Implementation must stay within it and obtain new approval for any wider change.

**S5-07 acceptance-evidence clarification (Protocol §7.1):** The frozen L4 one-time Reward evidence conflicted with the current Reward generator/configuration contract, which permits only null one-time IDs. This correction changes only the *test provenance*: normal Reward generation and multi-Reward Airplane remain catalog-generated; one-time compatibility uses approved constructors, strict Save v4 validation/mapping and a preloaded committed snapshot before any production-session operation. It neither permits a new one-time generator nor changes gameplay, Account/Reward semantics, the Save schema/version, migration or writer. Regression must prove exact reopen, one real guarded Move/Airplane claim, single Account claim ID/asset credit and operation-bound receipt, plus no duplicate claim/receipt on F5 or rejected/stale/uncertain outcomes; malformed/conflicting one-time facts still reject. Rollback is a reviewed revert of this documentation clarification and its scoped compatibility tests, preserving saved data and the existing generator/validator unchanged.

## 8. Scope, limitations and recovery

S5-07 is one capability. Internal implementation slices may separate public projection/receipt, control ownership/target, and tutorial/terminal browser integration, but they are not new product Tasks. S5-08 retains animation/audio/copy polish, S5-09 full presentation integration certification, Stage 6 full bilingual/skins/mobile adaptation, and later content tasks retain additional production Levels. No gameplay/economy balance, UI-owned solver, event bus, Manager, extra persistence, new Reward ledger or second authority is included.

Known limits remain: localStorage has no atomic CAS/absolute mutex; production currently has one Level, ordinary Rewards and no obstacles; a one-shot receipt can be missed if F5 occurs immediately after commit, while committed assets/claimed facts remain recoverable; browser native-event variations require the browser gate; Phaser >500 KB remains an observation. An unacknowledged event-only tutorial explanation can be revisited read-only without replaying its triggering command.

A fresh AI using AGENTS, Specification, Protocol, `PROJECT_STATUS`, this contract, S5-01–S5-06 contracts, source/tests and Git history must recover Stage 0–4 FROZEN, Stage 5 IN PROGRESS, the six corrected Attack boundaries, nine exact tutorial IDs, single guarded Save v4 authority, absent production L2–L5/one-time content, implementation acceptance tests, and exactly one next action: S5-07 Implementation.
