## 1. Ownership and route matrix

The application composition root owns one production session, one presentation adapter and one Shop purchase control for the page lifetime. Routes, Scenes, overlays, DOM nodes and cached ViewModels own only disposable presentation state. Navigation never creates a session, reads or writes Save directly, or implicitly abandons, dismisses, restarts or settles an Attempt. Scene reconstruction reuses the same root and Shop control. Browser reload reconstructs the root from committed authority, without replaying an envelope. HMR forces full reload or disposes the old root before replacement; it cannot leave two active roots.

The trusted adapter reads the production session and supplies sanitized public facts. The composition root alone passes those facts to pure UI projectors with the S5-02 exact structural/type and runtime secret-field checks. UI and Scenes do not receive raw Runtime, a catalog definition, hidden Reward/Board facts or a persistence capability. A route change invalidates a disposable ViewModel; it does not make the ViewModel authoritative.

`account-only` means `currentAttempt === null`. `recovery` means committed data is corrupt, unsupported, unprovable or unavailable; it is never treated as account-only/fresh. Phase-specific actions below always remain subject to the production command's own validation.

| Route / state | Account-only | Active | Pending encounter | Failed | Won | Recovery |
|---|---|---|---|---|---|---|
| Home | Account summary; Start/selection | Continue offered | Continue to pending decision | Return to terminal view | Return to terminal view | Recovery shell only; no fresh-game actions |
| Level Selection | Trusted selectable levels | View list; changing level requires confirmed replacement | Same, preserving pending encounter until committed replacement | Same, using legal dismiss before new Start | Same, using legal dismiss before new Start | Unavailable; no selection/start |
| Game entry/return | Only after committed Start | Reconstruct current Attempt | Reconstruct current pending decision | Reconstruct terminal state | Reconstruct terminal state | Unavailable; no fabricated Attempt |
| Shop | Accessible if validated Shop is available | **No entry**; explain restriction on current page | **No entry**; explain restriction on current page | **No entry**; explain restriction on current page | **No entry**; explain restriction on current page | Unavailable; no purchase |
| Settings | Read committed values; semantic commands | Same | Same | Same | Same | No uncommitted saved-value claim; reload/feedback available |
| Feedback | User-initiated mailto | Same | Same | Same | Same | Available from recovery shell |
| Recovery | Not shown as substitute for a normal route | Same | Same | Same | Same | Explicit non-destructive reload/diagnosis/feedback |

Home/menu return, opening selection, Settings or Feedback, and Game return are navigation only. Continue reprojects the existing Attempt; it is not Start/Retry. A request to reach Shop while an Attempt exists stays on the present route and shows centralized restriction copy. Only a separate, explicit, legally applicable `abandon` (active/pending) or `dismiss` (failed/won) that **commits successfully** can produce account-only authority; navigation then rereads it before allowing Shop. Uncertain, stale or rejected results cannot grant Shop access. Shop's production account-only guard remains authoritative. Invalid Shop configuration disables Shop non-destructively, without lease/persistence mutation.

Normal Settings use the two committed Save v4 preferences and existing `set-setting` command. No-op does not claim a Save write/revision; stale/lease/storage/uncertain and historical `not-writable` follow S5-04/S5-02 policies. Feedback opens only the Specification's `mailto:qingchen6757@gmail.com` on an explicit user activation; no automatic upload, diagnostics package or backend. All titles, controls, confirmations, restrictions, errors, empty states and accessibility labels use semantic centralized copy keys. Keyboard reachability, focus restoration on route/overlay changes and clear disabled/action states are required; this Task does not implement Stage 6 bilingual switching or mobile certification.

## 2. Corrected Shop exit and retained-operation contract

The application-lifetime root coordinates the adapter's purchase-owned retained envelope with the Shop control's `ready -> submitting -> receipt-disarmed` latch. A Shop exit is a narrow purchase operation: inspect/cancel only a retained envelope whose semantic intent is this Shop purchase; never call a broad cancellation that silently drops an unrelated operation. The current adapter's independent envelope cancellation and the Shop control's last-result-derived Retry action are not sufficient when used separately.

- During `submitting`, route/Scene teardown cannot assert cancellation or re-arm. Obtain and classify the outcome first; the purchase control remains synchronously disarmed against duplicate pointer/key activation.
- On a proven pre-new-head retainable purchase failure, Retry may be shown only while the exact immutable purchase envelope still exists. It reloads and verifies exact revision/runId/authority before one user-initiated replay. Leaving Shop cancels that **purchase** envelope and atomically invalidates the Shop Retry affordance. The latch remains `receipt-disarmed`; re-entry shows Reload, not a dead Retry or a ready Buy button. After explicit successful reload confirms account-only and valid Shop, a distinct Buy Again activation may re-arm a new purchase. No route change silently re-arms.
- A committed receipt remains `receipt-disarmed` across route/Scene changes; a new purchase requires the distinct Buy Again authorization and a fresh authority read. Domain rejection follows the already frozen deliberate reauthorization boundary.
- Stale revision/runId or ownership loss discards the old envelope, requires reload and a new action. `commit-persistence-commit-failure` remains conservative discard/reload absent exhaustive pre-head evidence. An uncertain commit is never replayed, even after reload; reload only discovers authority, and any later purchase is a new explicit action. Corrupt/unavailable reload cannot re-arm or claim success.
- Cancelling a retained purchase never rolls back a committed purchase, mutates Save, or cancels another feature's operation. Full browser reload drops all ephemeral envelope/latch state and recovers committed facts only; it never auto-purchases.

## 3. Ordinary cross-level replacement: two guarded commits

This is a narrow ephemeral presentation flow over existing production `abandon`, `dismiss` and `start` commands, not a second Runtime, transaction manager or persisted navigation fact. It is distinct from the existing atomic `Next` and `Replay` commands, which must never be decomposed into this flow. Same-level Continue preserves the current Attempt; Restart/Retry/Replay use their own existing legality and command paths. The current production catalog may contain only one level; the design adds no production Levels.

1. **Lock target and pure precheck.** Capture a stable target level ID and observed authoritative revision/runId. Against the same validated catalog used by production, check existence, unlock eligibility and configuration validity without side effects. Invalid/locked target stops with zero mutation. An historical current Attempt absent from today's catalog remains restorable and is not inserted into selectable levels.
2. **Explicit confirmation.** Show the target and the irreversible two-commit consequence. Cancellation writes nothing. Confirmation binds target ID and observed revision/runId; before the first mutation, explicitly call the production session's `reload()` to reread committed persistence authority (not its cached `read()`). If either identity changed, reload fails, or the phase no longer permits the selected lifecycle command, stop and request a new confirmation after showing the actual authority. Synchronously disarm duplicate confirmation activations; route destruction does not create a second first-step command. A competing write after this check is still rejected by the existing guarded revision/runId/lease gates; this precheck does not claim atomic CAS.
3. **First guarded commit.** Active/pending uses existing `abandon`; failed/won uses applicable existing `dismiss`. Account-only skips this commit. A rejection or proven pre-commit failure leaves old authority unchanged; an exact retained envelope may be user-retried only under S5-02 reload-and-match policy while the same flow remains active. Stale/lease conflict discards and reloads for a new action. An uncertain outcome must never be replayed or followed by Start until explicit reload establishes committed authority. Route cancellation drops a pending retry envelope, not an already committed fact.
4. **Reread and revalidate.** After a committed abandon/dismiss, the old Attempt is permanently gone. Explicitly call `session.reload()` to reread committed persistence authority, not cached `read()`. Require `currentAttempt === null`, then recheck target existence, unlock and current configuration against the same trusted catalog and current Account. Reload failure shows recovery; a newly present Attempt from another writer is shown as that actual Attempt and blocks Start; a newly invalid target leaves the observed account-only authority intact. No fictional rollback, overwrite or automatic resumption.
5. **Second guarded commit.** Only now construct a fresh immutable Start envelope with dispatch-time expected revision/runId and new stable technical creation facts. Submit the existing `start` command. Successful commit reprojects the new Attempt and enters Game. A rejected, stale, lease-lost, technical or uncertain Start does not restore the old Attempt; a subsequent explicit reload determines whether authority is account-only, another writer's Attempt, the successfully committed new Attempt, or recovery. Present that actual result without assuming account-only or replaying uncertain Start. A proven pre-commit retry, if offered while the flow survives, reuses the exact envelope after reload-and-match; it never rerolls runId, generation, Reward or Benben facts. Uncertain Start is never replayed.

A crash/reload between the two commits restores the actual committed authority (normally account-only if no other writer intervened) and forgets target, confirmation and envelope; it never automatically resumes Start. A failure to render after a committed Start is repaired by reopening and reprojecting committed authority, not by resubmitting Start. Duplicate clicks/key repeats/Scene reconstruction cannot produce a second abandon, dismiss or Start. A historical missing-catalog Attempt can Continue or be legally dismissed/abandoned as its phase permits; catalog-dependent Restart/Retry/Replay/Next may reject without corruption. It is not an ordinary selectable new level.

## 4. Trusted level-list projection

The trusted presentation capability uses the exact validated `PRODUCTION_LEVEL_CATALOG` object exported by the current production level module and used by production mutation commands. For each entry it calls existing `getLevelAccess(catalog, levelId, account.completedLevelIds)`. The output is a detached readonly allowlist: level ID, catalog order, and public locked/available/completed access presentation facts (plus current-level marker derived from the current Attempt where applicable). It contains no `LevelDefinition`, Reward payload/configuration, generation parameters/seed, hidden Board facts or mutable aliases. UI never duplicates unlock rules; it submits only a level ID, and the production Start command revalidates it.

Preserve S0-06's legal handoff: systems/presentation owns sanitized facts, ui owns projector input/ViewModel; the bootstrap/composition root alone shape-checks and hands facts to the pure UI projector. No systems-to-ui, ui-to-systems or executable-core import through ui. Historical missing-catalog Attempt information is a separate public current-Attempt summary, never a synthetic selectable catalog entry.

Controlled integration tests build one validated **multi-level test catalog** and pass that same object to the trusted projection and the existing catalog-injectable v4 execution seam. Production keeps the singleton catalog and production facade; no new production level, production catalog injection/backdoor, separate unlock table or hidden config exposure. Browser navigation tests use actual production catalog; controlled integration tests prove cross-level success and failures unavailable with its single level.

## 6. Frozen-boundary impact and scope

Protocol §7.1 record: **Reason** — MVP page navigation needs a concrete safe presentation contract over existing Stage 4/S5-02–S5-04 authority. **Affected contracts** — additive presentation route/level-list projection and narrow purchase-owned cancellation/latch coordination; existing S5-02 envelope classification, S5-03 purchase control, S5-04 Settings, Stage 4 lifecycle/Account, Save v4, Stage 2 guarded persistence and S0-06 dependencies are preserved. **Compatibility** — no existing gameplay/Shop/Settings result or command is reinterpreted; navigation and confirmation are ephemeral, full reload reads the same committed Runtime. **Schema/version/migration** — none. **Regression plan** — §5 plus existing Stage 1–5 quality and historical/migration/recovery checks. **Rollback** — a reviewed revert of scoped future presentation changes; never reset or downgrade persisted Save.

Known limits: localStorage remains best-effort coordination without atomic CAS; an account-only gap between the two cross-level commits is intentional and recoverable; the production catalog currently has one level, so shared-catalog controlled integration proves multi-level behavior; browser mailto handler availability is platform-dependent. No additional product decision is required for this design. S5-06 owns board gestures/input, S5-07 full terminal/tutorial presentation, S5-08 audio playback; Stage 6 owns bilingual/skins/mobile adaptation. No new gameplay, Level, Save field, framework, backend or second authority is authorized.
