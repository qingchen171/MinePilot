## 4. MVP 范围审计

未发现由未来需求反向进入 MVP 的大型系统。保留的“框架”只有 Theme/Skin/i18n/保存版本等已知必要扩展边界；明确禁止提前实现正式皮肤经济、账号、后端、排行榜、Analytics、反作弊和原生 App。

约 20 关、双语、移动端、商店、笨笨和四道具使该 MVP 仍属于“产品 MVP”而非最小技术原型，交付风险为中等。因此阶段门禁强制先完成无美术依赖的核心、存档与道具，再投入表现层；若时间不足，应减少内容数量或表现复杂度，不删除架构/测试门禁。

## 5. 未决项分类

以下未决项均已正确标为平衡/内容/发布阶段问题，不阻塞 Stage 0：价格、掉率、援助阈值、最终障碍比例、游戏名称、域名、正式素材、最低浏览器版本。

## 6. 可追踪性检查

- 61 项决定均在 Specification 附录索引中出现。

- 用户最担心的“改一个坏三个、越修越乱、最终重写”由单任务合同、两次失败 STOP、回归测试、Git 恢复点与人工验收共同控制。

## 7. 下一行动审计

唯一下一行动已冻结为：**Stage 0 / Task S0-01 - 项目入口与 Windows 环境基线核验。**

该任务必须只读，不安装、不初始化、不写游戏代码。它先解决当前最大未知：真正的游戏项目位置、旧 `D:\MinePilot` 的边界、Windows 工具链与恢复点。完成后才允许提出 S0-02。

## 8. 成功率与恢复

在严格执行门禁的前提下，完成 Stage 0 并进入可控增量开发的估计成功率：**85%-92%**。这是工程判断，不是统计保证。主要剩余风险是实际环境未知、MVP 内容量仍偏大、美术/移动端体验尚未验证。

恢复方案：控制文档为只读基线；每个 Task 独立 commit；任何阶段失败时退回最近 PASS 的 commit，并保持 Future Registry 与 Bug 证据，不在坏状态上连续抢救。
