# S5-02 Presentation Foundation Design Contract

Status: accepted Design Review, Attack Review, Design Correction and Final Design Correction; frozen for Implementation only after this documentation closeout passes Reviewer, PR/main Quality and Recovery gates. This document does not implement or authorize S5-03.

Authority: Specification and Development Protocol, S0-06, frozen Stage 2–4 contracts, and `11_Stage_5_Presentation_Architecture_Contract.md` remain controlling. The current production surface is `createProductionStage4Session()` with `read`, `reload`, and `execute`. Its mutation reasons are strings today; this contract does not change the Stage 4 API.

## 1. Single session and legal projection handoff

- The application composition root owns exactly one production session for a page lifetime. Scenes, routes, overlays and projectors never create a session or retain authoritative Runtime. A recreated Scene reuses the same presentation adapter. HMR must dispose the old root or force a full reload; it must not create competing live sessions.
- A presentation-owned narrow structural session port describes only the required `read/reload/execute` capabilities. `src/systems/presentation/` (or the equivalent one presentation capability) receives that port by injection and does not import `systems/persistence`. `src/main.ts` is the bootstrap-only adapter from the real session to that port. No new manager, bus, repository or state store.
- Raw `Stage4GameState` remains inside this trusted systems/presentation adapter. It invokes existing core queries, applies an explicit public-field allowlist, and emits detached readonly sanitized facts. It never passes raw Board/Attempt/Reward/Account objects or mutable aliases to `ui` or Scenes.
- The systems/presentation capability owns the `SanitizedPublicFacts` output type; `ui` owns its `PublicProjectionInput` and disposable readonly ViewModel types and pure projector. Neither layer imports the other, even type-only. Bootstrap imports both, statically checks exact structural/nested field compatibility (not merely a broad `Record<string, unknown>` assignment), and passes adapter-produced sanitized facts directly to the pure `ui` projector. Bootstrap performs wiring only, not sanitization, gameplay queries, projection rules or result classification. Scenes receive ViewModels and semantic intent capability, never raw Runtime.
- Tests must enforce the whitelist at runtime, including nested keys and alias isolation: hidden Safe/Mine and unclaimed Reward payloads are absent or indistinguishable in public projections. The architecture guard must continue to reject systems-to-ui, ui-to-systems and executable core imports from ui. Compile-time compatibility plus runtime secret-field tests are both required.

## 2. Intent and stable operation envelope

Scenes submit semantic player choices only. The adapter reads the current authoritative session at dispatch, captures `expectedRevision` and `expectedRunId`, obtains any required technical facts, and creates one deeply immutable envelope per logical submission. It includes the exact `DormantMutationIntent` facts needed for `session.execute`, not a candidate Board, Reward or Benben outcome. A changed authority or player choice requires a new envelope; an old envelope is never silently rebased to another revision/runId.

New `runId`/writer identity, generation seed, and Detection initialization seed are distinct technical capabilities. Writer identity remains owned by persistence and never enters a gameplay envelope. Generation facts follow the frozen deterministic generation contract; Detection entropy is independent of Stage 1 generation RNG. Secure-entropy absence/exception/invalid output leads to a non-destructive unavailable state before any mutation: no `Math.random` or guessed/fallback seed. Stable creation facts must survive Scene recreation and a proven pre-commit retry within the same adapter operation; they are neither persisted as an intent nor replayed after browser reload.

Only one unresolved submission may exist at the adapter boundary. S5-06 owns actual browser gesture, right-click, mode and double-click interpretation; S5-02 prevents a second envelope/submission while unresolved. Animation never holds or releases persistence authority. After a committed result, presentation may render the session-published Runtime; rejected results have no publishable candidate.

## 3. Exhaustive current observable result policy

The lists below are the complete current reason whitelist reachable from the production session through cached/read authority, lease acquisition, revision/runId guards, composition/domain validation, mapping, and guarded commit. Every listed reason maps to exactly one category. Classification is exact-string only, never prefix-based. Each row specifies commit safety, envelope policy, retry usefulness and recovery.

| Category | Current exact reasons | Commit safety | Envelope / retry / recovery |
|---|---|---|---|
| Terminal domain/no-op | `attempt-already-exists`, `no-attempt`, `invalid-phase`, `replay-not-entitled`, `level-not-found`, `level-locked`, `next-unavailable`, `no-alternative-mine-layout`, `generation-search-exhausted`, `pending-mine-encounter`, `run-failed`, `run-won`, `out-of-bounds`, `not-flaggable`, `already-flagged`, `already-unflagged`, `already-at-target`, `flagged`, `obstacle`, `revealed-mine`, `waiting`, `insufficient-inventory`, `usage-limit-reached`, `no-hidden-mine`, `no-pending-mine-encounter`, `lucky-priority`, `not-waiting`, `wrong-level`, `no-matching-entitlement`, `entitlement-unavailable`, `entitlement-used`, `card-already-exists`, `step-already-taken` | No commit for this submission | Discard; no retry of same rejected intent. Explain with copy key; a changed choice is a new action. |
| Stale authority / ownership | `revision-conflict`, `run-id-conflict`, `owned-by-another-session`, `commit-revision-conflict`, `commit-writer-not-owner`, `commit-lease-expired` | Rejected before this command's commit; another writer may have changed authority | Discard; reload, then require a new user action. Never rebase/replay the old envelope. |
| Proven pre-new-head technical failure, conditional | `storage-failure`, `verification-failure`, `commit-lease-storage-failure`, `commit-persistence-commit-failure` | No new committed head for the proven source set; this classification requires exhaustive failure-stage evidence in S5-02 Implementation | May retain exact envelope only after reload and exact revision/runId/authority match, and only for a useful user-initiated retry. If evidence is incomplete for any source, classify the entire observable reason conservatively: discard/reload/diagnose, no replay. |
| Uncertain commit outcome | `commit-commit-outcome-uncertain` | A new head may already be committed | Invalidate permanently; never replay, even after reload. Block mutation until explicit reload resolves authority; new user action only. |
| Corrupt / unavailable recovery | `invalid-json`, `invalid-save`, `revision-mismatch`, `unavailable-snapshot`, `commit-persistence-load-failure`, `invalid-lease` | No publishable result; persisted authority may be unreadable or unprovable | Discard; non-destructive recovery view, explicit reload/diagnosis; no reset, overwrite, fresh bootstrap or automatic retry. |
| Pre-commit technical/validation failure | `invalid-request`, `invalid-creation-facts`, `invalid-level`, `invalid-placement`, `invalid-rewards`, `generation-configuration-mismatch`, `invalid-game-state`, `invalid-encounter-target`, `invalid-detection-seed`, `seed-unavailable`, `invalid-card-derivation`, `invalid-authority`, `reward-invalid-board-transition`, `reward-invalid-authority`, `reward-asset-overflow`, `terminal-not-applicable`, `terminal-rejected`, `invalid-candidate`, `revision-overflow`, `invalid-runtime`, `not-writable`, `commit-invalid-next-revision` | No commit on this path | Discard and diagnose; retrying the identical invalid intent is not useful. Reload only if diagnostic handling indicates changed authority. |

Successful `committed` closes the envelope and renders published authority. A future/unrecognized status or reason is not added by name pattern: conservatively discard, block automatic retry, reload and diagnose. Any safe-retry promotion requires source-level commit-point proof and regression tests, not a user-visible error label. In particular, `commit-persistence-commit-failure` is retainable only if **all** currently reachable subfailures are proven before successful new-head write, including serialized DTO and storage stages. The `new-head-write` ambiguity remains `commit-commit-outcome-uncertain`; a failed post-commit backup update is a committed success. Missing exhaustive evidence means the whole `commit-persistence-commit-failure` reason uses conservative discard/reload.

Route cancellation discards a pending retry envelope but cannot undo a commit. Scene recreation does not regenerate unresolved facts. Browser reload loses the envelope and reads committed authority. Foreground/storage-change notification only requests `session.reload`; it never interprets A/B slots or triggers a command. Reload failure blocks mutation and leaves recovery UI available.

## 4. View, copy and implementation evidence

Pure ViewModels expose public Board appearance, current position/current-number query result, visible explored/flag/revealed/obstacle facts and committed inventory/outcome only. Unknown Safe and Hidden Mine have identical public appearance; unrevealed Reward facts stay hidden. No ViewModel is persisted or used as authority. The adapter uses existing core queries, including `getCurrentCellMineCount`; ui/Scene does not count neighbors or decide victory, Item eligibility, Reward or persistence behavior.

All player-visible messages, labels, confirmations, errors and accessibility text use centralized semantic copy keys and config resources; technical reason-to-copy mapping is centralized. This is a Stage 5 foundation, not Stage 6 translation delivery. No player-visible literals should spread into Scenes.

Implementation acceptance requires unit tests for exact result whitelist and conservative unknown fallback, immutable envelope and entropy failure, public-field whitelist/no alias/hidden-information equivalence, projector purity and semantic copy keys; integration with the real production session for committed/rejected/stale/uncertain/reload behavior and exact-fact retry; architecture checks for the legal bootstrap handoff and forbidden imports. Prove every claimed pre-head failure stage, including a mutation sanity check that an intentionally misclassified uncertain result fails. Reuse Stage 2–4 regressions. Browser gesture interpretation and complete Phaser journeys remain S5-06/S5-09, not S5-02.

## 5. Boundaries and recovery

No Shop authority/prices, settings/tutorial persisted facts, Save version change, gameplay Scene, animation/audio assets, Stage 6 bilingual/skins/mobile, or new gameplay/persistence authority is part of S5-02. Product choices are deferred to S5-03 Shop Design and S5-04 settings/tutorial Design as in the Stage 5 contract. Existing localStorage best-effort coordination and non-atomic CAS limitations remain.

This design freeze authorizes only the next S5-02 Implementation task after its closeout gates pass. It does not itself activate a presentation adapter or change production behavior. Recovery must identify the S5-01 contract, this exact reason whitelist and projection handoff, the unchanged Stage 4 production authority, and one next action in `PROJECT_STATUS`.
