## 1. Authority and ownership

The existing application composition root owns one production session, presentation adapter and navigation control for the page lifetime. A Game Scene, DOM board, route or animation owns only disposable display/input state. They receive the existing sanitized public ViewModel and a semantic `move`/`flag` submission capability, never raw Runtime, hidden Board/Reward facts, a storage adapter or a second persistence authority. The trusted adapter performs core queries and sanitization; the bootstrap-only handoff to pure `ui` projection follows S5-02 and S0-06. No Scene/DOM code calculates Mine truth, neighbor counts, Victory, Reward, Item eligibility or legal movement.

One browser activation may submit one semantic intent with a target coordinate. The S5-02 adapter captures current revision/runId and stable technical facts at dispatch, submits through the existing guarded Save v4 production path, and renders only a committed re-projection. A rejected/stale/lease-lost/storage-failed/uncertain result supplies no fictional character destination. Uncertain commit is never replayed; reload determines committed authority. No animation callback performs gameplay or Save mutation.

## 2. Public Board and character appearance

The sanitized appearance allowlist is `unknown | flagged | explored | obstacle | revealed-mine`, with detached row-major cells and public dimensions. `unknown` Safe and hidden Mine must have identical visual treatment, text, ARIA label, hover/focus affordance, disabled state and pre-commit interaction behavior; no hidden Mine or unrevealed Reward payload, seed, provenance or raw Cell reaches Scene/UI. A flag does not reveal its underlying truth. An obstacle and revealed Mine are already public; neither becomes a movement shortcut.

`waiting` is shown off-board. `on-board` is shown on its committed explored Safe coordinate. `revealed-mine-occupancy` is shown on its committed revealed Mine coordinate; ordinary movement may leave it but cannot return to that revealed Mine. The Scene does not create a separate Lucky/Revive position. The current-cell number comes only from the existing trusted `getCurrentCellMineCount` result in public projection: a positive value is shown only for the current eligible Safe; zero produces a gentle safety cue, not a printed `0`; unavailable/waiting/occupancy hides the number. An explored Safe left behind retains its trace but not the old current number.

Only `active` with `waiting`, `on-board` or `revealed-mine-occupancy` offers board actions. Pending encounter, failed and won phases, account-only and Recovery do not offer board submissions; the authoritative command remains the final legality gate. Pending UI may show only committed public phase/position, not infer a hidden Mine conclusion from the last click. S5-07 owns the complete pending/terminal/Item/tutorial presentation, not this board input contract.

## 3. Desktop, touch and keyboard input

On desktop, primary click on a board cell **always** means Move; secondary click **always** means Flag toggle and suppresses the browser context menu only over the board cell. A visible Flag button never changes those mouse meanings. It acts on one explicitly highlighted public target coordinate, selected by the currently focused cell or most recently pointed-to cell. The coordinate remains visibly identified when focus moves to the button; with no valid target, the button is unavailable. The button submits only Flag, never a preceding Move. A cell's focus is selection, not character movement. Invalid targets remain subject to the existing command rejection, without leaking hidden truth through affordances.

Keyboard cell focus uses visible row/column location and standard grid movement; focus movement submits nothing. A single Enter/Space activation on a focused cell uses the primary Move action. The visible Flag button is keyboard reachable and Enter/Space on it toggles the explicitly displayed target. Focus remains on a stable coordinate after a committed re-projection when the same Attempt/board still exists; if that coordinate or Attempt no longer exists, focus returns to the Game heading or another safe page landmark. Do not convert a key hold or browser-generated follow-on click into another command.

Touch uses a distinct, visibly announced Move/Flag mode to avoid accidental actions. That mode interprets touch activation only; it does not alter desktop primary/secondary semantics. This is the minimum MVP input feedback, not Stage 6 mobile certification, responsive polish or a new gameplay rule.

## 4. One native activation, not a time lock

The DOM board is the sole board command submission surface. One input interpreter owns native `click`, `contextmenu`, pointer sequence and keyboard activation; Phaser never dispatches a board command. Pointer events identify source/press identity and maintain target/focus, but do not independently submit. A primary pointer activation submits on its `click`; a secondary pointer activation submits on its `contextmenu`; `dblclick` is non-submitting. Correlate generated events to the same physical press/target so a `click` and a companion event cannot each submit. The continuation of a native multi-click sequence on the **same target** is one logical activation even if the first commit finished synchronously; a new press on a **different target** is immediately eligible. Do not use a global elapsed-time debounce or wait for animation to release command authority.

Own keyboard activation through one down/up sequence: repeated `keydown` does not submit, one valid `keyup` can submit, and its browser-synthesized `click` cannot submit again. An assistive-technology activation that arrives only as a `click` remains usable once. Route change, Scene disposal, authority change and Recovery invalidate outstanding press/target state. S5-02 independently prevents a second unresolved operation/envelope; the native-event rule also covers a synchronous committed result. A safe retained retry reuses the exact immutable envelope only under S5-02 policy; an event continuation never creates a retry or fresh envelope.

## 5. Shared DOM/Phaser geometry and lifecycle

A single board presentation layout owns one measured CSS content rectangle, top-left origin, logical board dimensions, uniform cell size and any centered letterbox offsets. Both the DOM hit grid and Phaser drawing consume that same layout snapshot; neither computes an independent board rectangle. Logical coordinate is `(x = column, y = row)`, with `index = y * width + x`. DOM cell nodes carry their explicit logical coordinate and are the only hit targets; Phaser draws from the same coordinate/layout but does not perform pixel-to-cell gameplay hit testing. Points outside the displayed board rectangle do not select a cell.

Resize, browser zoom, DPR changes and scrolling trigger or use a fresh shared layout measurement before hit targets and Phaser visuals are considered aligned. DPR may change raster sharpness, not logical coordinate or cell ownership. While layout is invalid/stale, the old DOM hit surface cannot submit; rebuild it together with the Phaser geometry, then restore safe focus. Route change or Scene reconstruction discards old hit nodes, pending visuals and animation and reconstructs from the latest committed public projection. No cached ViewModel or tween becomes authority. Paths between committed origin and destination are presentation-only: intermediate cells never explore, hit Mines, claim Reward or settle Victory. A committed state may be displayed immediately without animation; S5-08 owns later animation/audio polish.
